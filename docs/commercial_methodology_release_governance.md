# Daily Alpha Commercial Methodology Release Governance

Status: **commercial-beta design / staging evidence only**.

This specification defines how a future customer-visible Daily Alpha methodology may move from research into a released product without rewriting historical evidence, silently migrating beta cohorts, or mixing incompatible performance eras. It does not authorize a launch, public claim, production deployment, strategy promotion, customer communication, billing, TradingView mutation, brokerage action, or live trading.

## Lifecycle

`DRAFT_RESEARCH -> VALIDATING -> APPROVED_FOR_FUTURE_RELEASE -> ACTIVE -> DEPRECATED -> RETIRED`

An active release may instead move to `ROLLED_BACK -> RETIRED`. Terminal or rolled-back versions never silently reactivate; a return to prior behavior requires an explicit auditable release/version decision.

`APPROVED_FOR_FUTURE_RELEASE` means evidence has passed the methodology-validation contract. It is not customer-launch authorization.

## Immutable identity

Every methodology version must retain:

- methodology ID and human-readable version;
- source commit/build identity;
- parameter/configuration hash;
- point-in-time input-data contract version;
- performance-methodology/benchmark/cost reference;
- material-change class;
- predecessor identity where applicable;
- effective timestamp and release-manifest identity when active.

A customer-visible report or performance observation without resolvable methodology identity fails closed.

## Material change matrix

| Change class | Example | Minimum evidence invalidated before future activation |
| --- | --- | --- |
| PRESENTATION_ONLY | wording/layout with no result change | rendering/provenance checks |
| DATA_SOURCE_OR_PARSER | vendor field/parser/source change | data-quality, provenance, replay, rights review |
| RANKING_OR_FEATURE | factor/rank feature change | model validation, factor/forensics evidence, performance methodology |
| ENTRY_EXIT_RULE | breakout/exit threshold change | historical holdout + prospective shadow/model governance |
| PORTFOLIO_RISK_OR_SIZING | sizing, hedge or concentration change | portfolio-risk, drawdown, capacity, performance evidence |
| INSTRUMENT_EXPRESSION | shares/options/leveraged proxy selection | option/execution/capacity/performance evidence |
| PERFORMANCE_METHOD | benchmark, costs, option marks, return calculation | performance methodology and claim evidence |
| EMERGENCY_ROLLBACK | defect/operational rollback | incident/release evidence and explicit rollback record |

Exact launch-gate dependencies should be wired to #171/#172 rather than duplicated in this module.

## Customer and archive behavior

1. Every report displays or exposes its methodology version and effective/as-of context.
2. Historical reports preserve the methodology that actually generated them.
3. Delivery retries resend the immutable original report artifact; they do not regenerate an old report under the currently active methodology.
4. Beta cohorts may be pinned to a methodology only through explicit entitlement/product policy. A release job cannot silently migrate a pinned cohort.
5. Archive/search projections can filter by methodology era and show predecessor/successor relationships.
6. Planned methodology changes are distinct from correction/retraction events under #200/#201.

## Performance evidence

- `ACTUAL`, `PAPER`, `BACKTEST`, and `HYPOTHETICAL` remain separate.
- Methodology identity is an additional grouping dimension.
- One performance line may combine multiple methodology eras only under an explicit, predeclared chaining policy with clear era boundaries.
- Historical observations are never retroactively relabeled as if generated by a newer methodology.
- Benchmark/cost/performance-method changes carry their own version references.

## Staging acceptance tests

A commercial-beta evidence package should prove at minimum:

1. v1 -> v2 migration leaves every v1 report/evidence hash unchanged.
2. A v1 delivery retry cannot produce v2 content under the v1 report ID.
3. Missing/unknown methodology identity blocks customer publication and performance inclusion.
4. `ACTIVE` requires validation evidence, a release-manifest reference, and explicit release approval evidence.
5. A rolled-back or retired version cannot silently become active again.
6. A beta cohort pinned to v1 is not migrated by a v2 release operation.
7. DR/restore preserves active/deprecated/retired state and cannot resurrect a terminal version.
8. Material-change classification invalidates the appropriate launch evidence families.

## External-review boundary

Before a real commercial launch, customer-facing change notices, performance-era presentation, disclosures, terms/privacy/support language, and any jurisdiction-specific notification obligations require the separate external-review process in #97. Repository controls should not state that a particular implementation is legally compliant.
